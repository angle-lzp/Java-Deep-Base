# LangGragh 开 Agent 整技术栈

如果目标是做一个 **可维护、可控、可上线的 AI Agent**，并且核心框架选 **LangGraph**，那技术栈不要只围绕“Agent 框架”选，而要按生产系统来设计。

我建议的完整技术栈可以分成这几层：

```text
前端/客户端
  -> API 服务层
  -> Agent 编排层 LangGraph
  -> 模型层 LLM / Embedding / Reranker
  -> 工具层 Tools / Function Calling
  -> 数据层 PostgreSQL / Redis / Vector DB / Object Storage
  -> 任务层 Queue / Worker
  -> 观测层 Logs / Traces / Metrics / Evaluation
  -> 安全与部署层 Auth / Guardrails / CI/CD / Kubernetes
```

## 推荐技术栈总览

| 层级 | 推荐技术 | 作用 |
|---|---|---|
| Agent 编排 | **LangGraph** | 定义 Agent 状态、节点、边、分支、循环、人工审核 |
| LLM 组件 | LangChain / 原生 SDK | 调用模型、工具绑定、消息封装 |
| API 后端 | **FastAPI** | 对外提供 HTTP/SSE/WebSocket API |
| 类型校验 | **Pydantic** | 请求、响应、工具参数、结构化输出校验 |
| 主数据库 | **PostgreSQL** | 用户、会话、任务、审计、业务数据 |
| 向量数据库 | pgvector / Qdrant / Milvus / Weaviate | RAG 检索 |
| 缓存 | **Redis** | 会话缓存、限流、短期状态、任务锁 |
| 消息队列 | Celery + Redis/RabbitMQ / Dramatiq / RQ | 长任务、异步工具调用、批处理 |
| 对象存储 | S3 / MinIO / Azure Blob | 存 PDF、图片、上传文件、生成文件 |
| RAG 框架 | LlamaIndex / LangChain retriever / Haystack | 文档加载、切分、索引、检索 |
| 模型服务 | OpenAI / Azure OpenAI / Anthropic / Gemini / vLLM / Ollama | 大模型推理 |
| Embedding | OpenAI embedding / bge / jina / nomic | 文本向量化 |
| Reranker | bge-reranker / Cohere Rerank / Jina Reranker | 提升检索结果质量 |
| 观测追踪 | **LangSmith** / OpenTelemetry / Grafana | 查看 Agent 每一步执行 |
| 日志 | structlog / logging + ELK/Loki | 系统日志和错误排查 |
| 评估 | LangSmith Eval / Ragas / DeepEval / Promptfoo | 回归测试、RAG 质量、Agent 行为评估 |
| 安全护栏 | Guardrails AI / NeMo Guardrails / 自定义规则 | 输入输出过滤、权限、敏感信息控制 |
| 部署 | Docker + Kubernetes / Docker Compose | 服务部署 |
| CI/CD | GitHub Actions / GitLab CI / Azure DevOps | 自动测试、构建、发布 |
| 前端 | React / Next.js / Vue | Chat UI、任务面板、审核界面 |
| 文档与接口 | OpenAPI / Swagger / MkDocs | API 文档、开发文档 |

## 核心层：LangGraph

LangGraph 是整个 Agent 的“流程大脑”。

你会用它定义：

- Agent 的状态 State
- 每一步执行节点 Node
- 节点之间的流转 Edge
- 条件分支 Conditional Edge
- 循环重试
- 工具调用
- 人工审核
- 错误处理
- 中断与恢复
- 多 Agent 协作

典型结构：

```text
用户输入
 -> 意图识别
 -> 权限检查
 -> 是否需要 RAG
 -> 检索知识库
 -> 是否需要调用工具
 -> 调用业务工具
 -> 结果校验
 -> 是否需要人工审核
 -> 生成最终回答
 -> 记录审计日志
```

LangGraph 适合把 Agent 做成“可控流程”，而不是让模型自由发挥。

## API 层：FastAPI

LangGraph 本身不是完整 Web 服务，所以你通常需要 FastAPI 包一层。

FastAPI 负责：

- 用户登录后的请求入口
- Chat API
- 文件上传 API
- 流式输出 SSE/WebSocket
- 任务查询 API
- 管理后台 API
- 权限校验
- 请求参数校验
- 调用 LangGraph 执行 Agent

推荐 API 形式：

```text
POST /chat
POST /chat/stream
POST /files/upload
GET  /sessions/{session_id}
GET  /runs/{run_id}
POST /feedback
POST /human-review/{task_id}
```

## 数据层

生产级 Agent 至少需要三类数据存储。

**PostgreSQL**

存结构化数据：

- 用户
- 会话
- 消息记录
- Agent 执行记录
- 工具调用记录
- 权限配置
- 审计日志
- 反馈数据
- 业务数据映射

推荐配套：

```text
PostgreSQL + SQLAlchemy/SQLModel + Alembic
```

**Redis**

用于高频、临时、短生命周期数据：

- 会话缓存
- 分布式锁
- 限流
- 短期任务状态
- Celery broker
- Token 计数缓存
- 工具调用结果缓存

**对象存储**

用于存文件：

- PDF
- Word
- Excel
- 图片
- 日志附件
- Agent 生成的报告
- RAG 原始文档

推荐：

```text
S3 / MinIO / Azure Blob
```

## RAG 层

如果你的 Agent 需要“查知识库”，就需要 RAG 技术栈。

推荐组件：

```text
文档加载：
- LlamaIndex
- LangChain Document Loaders
- Unstructured

文档解析：
- PyMuPDF
- python-docx
- pandas
- unstructured
- markitdown

文本切分：
- RecursiveCharacterTextSplitter
- Semantic Splitter
- Markdown Header Splitter

向量化：
- OpenAI Embedding
- bge-m3
- jina-embeddings
- nomic-embed-text

向量库：
- pgvector
- Qdrant
- Milvus
- Weaviate

重排序：
- bge-reranker
- Cohere Rerank
- Jina Reranker
```

一个质量较好的 RAG 流程通常是：

```text
上传文档
 -> 解析
 -> 清洗
 -> 切分
 -> 生成 embedding
 -> 存入向量库
 -> 用户提问
 -> 向量检索
 -> rerank
 -> 组装上下文
 -> LLM 回答
 -> 引用来源
```

如果你想快一点落地，RAG 层可以用 **LlamaIndex**；如果你想全部自己控制，可以用 LangChain retriever + 自己的数据管道。

## 工具调用层

Agent 真正有用，通常靠 Tools。

工具可以是：

- 查询数据库
- 调用企业 API
- 查询设备状态
- 查询订单
- 生成报表
- 发送邮件
- 创建工单
- 查询知识库
- 调用 Python 函数
- 调用外部 HTTP 服务

工具层建议单独封装，不要直接写在 LangGraph 节点里。

推荐结构：

```text
app/
  agents/
    graph.py
    state.py
    nodes.py
  tools/
    order_tool.py
    database_tool.py
    email_tool.py
    device_tool.py
    rag_tool.py
  services/
    order_service.py
    user_service.py
    permission_service.py
  repositories/
    order_repository.py
    session_repository.py
```

原则是：

> Agent 负责决策和编排，Tool 负责能力暴露，Service 负责业务逻辑，Repository 负责数据访问。

这样后期才好维护。

## 异步任务层

很多 Agent 任务不能只靠一次 HTTP 请求完成。

比如：

- 处理大文件
- 长时间分析
- 批量生成报告
- 调用慢接口
- 多轮工具执行
- 定时任务
- RAG 文档入库

这时需要任务队列。

推荐：

```text
简单项目：
- RQ + Redis
- Dramatiq + Redis

中大型项目：
- Celery + Redis
- Celery + RabbitMQ
```

典型用法：

```text
用户提交任务
 -> API 创建 task_id
 -> 投递到队列
 -> Worker 执行 LangGraph
 -> 更新任务状态
 -> 前端轮询或 WebSocket/SSE 接收结果
```

## 观测与调试

生产级 Agent 一定要能看清楚每一步发生了什么。

至少要记录：

- 用户输入
- Agent 选择了哪个路径
- 调用了哪些工具
- 每个工具的输入输出
- 检索到了哪些文档
- 消耗了多少 token
- 模型返回了什么
- 哪一步失败了
- 延迟是多少
- 最终回答是什么
- 用户反馈如何

推荐：

```text
LangSmith：
- Agent trace
- Prompt 版本
- 调用链路
- 数据集评估

OpenTelemetry：
- 服务链路追踪

Prometheus + Grafana：
- 指标监控

Loki / ELK：
- 日志检索
```

关键指标：

```text
成功率
失败率
平均响应时间
P95/P99 延迟
Token 消耗
每次请求成本
工具调用成功率
RAG 命中率
用户满意度
人工介入率
```

## 评估体系

这是很多 Agent 项目容易忽略的一层。

没有评估体系，Agent 每次改 Prompt、换模型、调检索参数，都不知道是变好了还是变差了。

推荐工具：

```text
pytest：
- 单元测试
- 工具函数测试
- LangGraph 节点测试

Ragas：
- RAG 质量评估
- faithfulness
- answer relevancy
- context precision
- context recall

DeepEval：
- Agent 输出评估
- 自定义指标

Promptfoo：
- Prompt 回归测试
- 多模型对比

LangSmith Eval：
- Trace + 数据集评估
```

建议准备几类测试集：

```text
正常问题集
边界问题集
权限问题集
恶意输入集
工具失败集
RAG 无答案集
多轮对话集
业务高频问题集
```

## 安全与权限

AI Agent 能调用工具，就必须做权限控制。

不能让模型直接决定所有事情。

需要控制：

- 用户是否有权限访问某数据
- 用户是否能调用某工具
- 工具参数是否合法
- 是否允许执行写操作
- 是否需要人工确认
- 是否包含敏感信息
- 是否有越权查询
- 是否有 Prompt Injection
- 是否泄露系统提示词

推荐做法：

```text
权限：
- RBAC / ABAC
- OAuth2 / OIDC
- JWT / Session

敏感信息：
- PII 检测
- 数据脱敏
- 日志脱敏

工具安全：
- 工具白名单
- 参数校验
- 只读工具和写入工具分离
- 高风险操作人工确认

Prompt Injection 防护：
- 文档内容与系统指令隔离
- 检索内容标记为不可信
- 禁止模型根据文档内容修改系统规则
```

写操作必须加确认，比如：

```text
查询订单：可以直接执行
取消订单：必须人工确认
发送邮件：最好人工确认或预览
删除数据：强制人工确认
```

## 我的推荐结论

如果你要做的是 **可维护、可控、可上线的 AI Agent**，我推荐这套主线：

```text
LangGraph + FastAPI + PostgreSQL + pgvector/Qdrant + Redis
+ Celery + S3/MinIO + LangSmith + Ragas/DeepEval
+ Docker/Kubernetes + React/Next.js
```

如果你的 Agent 还需要企业知识库，就加：

```text
LlamaIndex + Embedding Model + Vector DB + Reranker
```

如果你的 Agent 要接业务系统，就重点做好：

```text
Tools 封装
权限控制
人工确认
审计日志
错误恢复
观测追踪
```

真正决定 Agent 能不能上线的，不只是 LangGraph，而是这几件事：**状态可控、工具安全、结果可评估、过程可追踪、失败可恢复、权限可约束**。LangGraph 负责其中的“流程与状态”，其他技术栈负责把它变成一个可靠的工程系统。
