# Teams Chatbot 应用安装与网络配置指南

本文档整理了 Teams Chatbot 开发过程中的以下三个环节：

- 将应用安装到 Microsoft Teams
- 自建服务器的网络条件与安全要求
- 回复当前消息与主动推送消息的区别

---

## 1. 将应用安装到 Microsoft Teams

### 1.1 开发测试阶段：上传自定义应用

在完成 Teams App Manifest 和应用包之后，可通过 Teams 客户端上传自定义应用进行测试。

操作路径：

```text
Microsoft Teams
→ Apps
→ Manage your apps
→ Upload an app
→ Upload a custom app
→ 选择 Teams 应用 ZIP 包
```

Teams 应用 ZIP 包中必须直接包含以下文件：

```text
manifest.json
color.png
outline.png
```

正确的 ZIP 包结构：

```text
it-assistant.zip
├── manifest.json
├── color.png
└── outline.png
```

不要在 ZIP 包中额外嵌套一层目录。例如，下面的结构可能导致 Teams 无法正确识别应用包：

```text
it-assistant.zip
└── appPackage
    ├── manifest.json
    ├── color.png
    └── outline.png
```

### 1.2 用户如何打开 Chatbot

应用安装完成后，用户可以在 Teams 中通过以下路径打开：

```text
Apps
→ 搜索 IT Assistant
→ Add 或 Open
→ 进入与 Agent 的一对一聊天窗口
```

如果应用的 Manifest 配置了 `personal` scope，用户可以直接在聊天窗口输入问题，不需要使用 `@` 提及 Agent。

示例：

```text
查询服务器 CN-DG-APP-001 的运行状态。
```

如果 Manifest 同时配置了 `groupChat` 或 `team` scope，Agent 还可以被添加到群聊或 Team 频道中。在群聊和频道中，用户通常需要明确 `@` Agent：

```text
@IT Assistant 查询今天未关闭的 P1 工单。
```

### 1.3 生产环境发布

生产环境不建议让每位用户手动上传 ZIP 包。推荐的企业内部发布流程是：

```text
开发团队准备 Teams 应用包
→ 提交到组织的 Teams 应用目录
→ Teams 管理员审核
→ 在 Teams Admin Center 中允许或发布应用
→ 通过 App Setup Policy 自动安装或固定应用
```

建议分别维护以下环境：

```text
IT Assistant Dev
IT Assistant UAT
IT Assistant Prod
```

每个环境应使用独立的：

- Teams App ID
- Bot App ID
- Azure Bot Resource
- Messaging Endpoint
- 后端配置
- 日志和监控资源

这样可以防止开发或测试环境的消息误发到生产系统。

## 2. 自建服务器需要满足的网络条件

如果 Chatbot 后端部署在公司自己的 Linux Server、Windows Server、VMware VM、Docker Server 或 Kubernetes 集群中，需要同时满足入站和出站网络要求。

### 2.1 入站网络要求

Teams 和 Bot Channel 必须能够通过 HTTPS 访问 Chatbot 的 Messaging Endpoint，例如：

```text
https://chatbot.company.com/api/messages
```

通常需要开放：

```text
协议：HTTPS
端口：TCP 443
路径：/api/messages
```

推荐网络结构：

```text
Microsoft Teams / Bot Channel
        ↓ HTTPS 443
公网 DNS：chatbot.company.com
        ↓
企业防火墙
        ↓
WAF / F5 / NGINX / Reverse Proxy
        ↓
内部 Chatbot Backend
        ↓
http://10.10.20.30:3978/api/messages
```

不要直接将内部 Chatbot 进程的端口暴露到公网。应通过企业现有安全入口进行代理，例如：

- F5 BIG-IP
- NGINX
- Azure Application Gateway WAF
- Azure API Management
- 企业 DMZ 反向代理
- 负载均衡器

### 2.2 公网 DNS 与 TLS 证书

公网 DNS 应将域名解析到 WAF、反向代理或负载均衡器的公网地址：

```text
chatbot.company.com
→ 公网 IP 或公网负载均衡地址
```

HTTPS 证书应满足以下要求：

- 证书在有效期内
- 域名与证书中的 Subject Alternative Name 匹配
- 证书链完整
- 使用受公共信任的证书颁发机构
- TLS 版本和加密套件符合公司安全标准

如果使用只有公司内部设备信任的私有 CA 证书，Microsoft 的云端服务可能无法建立受信任的 TLS 连接。

### 2.3 WAF 和反向代理注意事项

WAF、F5 或 NGINX 转发请求时，需要保留必要的 HTTP Header，尤其是：

```text
Authorization
Content-Type
Host
X-Forwarded-For
X-Forwarded-Proto
```

不要让反向代理删除或改写 Bot Channel 请求中的 `Authorization` Header，否则后端无法验证消息来源。

建议为 `/api/messages` 配置：

- 只允许 `POST`
- 限制最大请求体大小
- 启用请求超时
- 启用访问日志
- 不记录完整 Authorization Token
- 配置合理的速率限制
- 保留 Correlation ID 或 Request ID

### 2.4 出站网络要求

Chatbot 后端通常需要访问以下外部或内部服务：

```text
Chatbot Backend
├── HTTPS 443 → Microsoft Teams / Bot Connector 服务
├── HTTPS 443 → Microsoft Entra ID
├── HTTPS 443 → Azure OpenAI / Microsoft Foundry
├── HTTPS 443 → 公司内部 API
└── 数据库端口 → 公司内部 DB
```

常见数据库端口包括：

```text
SQL Server：TCP 1433
Oracle：TCP 1521
PostgreSQL：TCP 5432
MySQL：TCP 3306
```

如果公司服务器完全禁止互联网出站，可能出现以下现象：

- 能访问内部数据库，但无法调用 Azure OpenAI
- 无法从 Microsoft Entra ID 获取 Token
- 无法通过 Bot Connector 将消息返回 Teams
- Bot 请求认证或 Token 刷新失败

因此，需要由网络和安全团队为必要的 Microsoft 服务配置受控 HTTPS 出站策略。

### 2.5 内部 API 和数据库访问原则

优先推荐通过内部 API 访问业务数据：

```text
Chatbot Backend
    ↓ HTTPS + OAuth 2.0 / mTLS
Internal API Gateway
    ↓
Internal Service
    ↓
Database
```

原因包括：

- 统一身份认证和授权
- 可以执行行级权限控制
- 可以过滤敏感字段
- 可以限制返回记录数量
- 可以记录审计日志
- 可以隔离数据库结构变化
- 可以实施限流和缓存

如果确实需要让 Chatbot 后端直接访问数据库，至少应满足：

- 使用专用只读账号
- 只授权指定 Schema、View 或 Stored Procedure
- 禁止 INSERT、UPDATE、DELETE
- 所有查询都使用参数化 SQL
- 不执行模型生成的任意 SQL
- 设置连接超时和查询超时
- 设置最大返回行数
- 对返回字段进行脱敏

### 2.6 网络测试方法

在部署 Chatbot 后端的服务器上，按以下顺序测试网络。

#### 检查 DNS

```bash
nslookup monitoring-api.company.local
```

#### 检查 HTTPS

```bash
curl -vk https://monitoring-api.company.local/health
```

#### 检查数据库端口

```bash
nc -vz sql01.company.local 1433
```

#### 使用应用身份测试内部 API

```bash
curl \
  -H "Authorization: Bearer $TOKEN" \
  https://monitoring-api.company.local/api/servers/CN-DG-APP-001
```

故障排查顺序建议固定为：

```text
1. DNS 是否能够解析
2. TCP 端口是否能够连接
3. TLS 证书是否能够验证
4. 身份认证是否成功
5. 业务授权是否通过
6. API 或 SQL 查询是否正确
```

## 3. 回复当前消息与主动推送消息的区别

### 3.1 回复当前用户消息

这是第一版 Chatbot 最常用、也最容易实现的方式。

完整流程：

```text
用户向 Agent 发送问题
→ Teams 将消息发送到 Messaging Endpoint
→ Chatbot 后端接收 Activity
→ Agent 调用模型和内部工具
→ Chatbot 后端获得最终答案
→ 使用当前 Activity Context 回复
→ 用户在原 Teams 对话中看到答案
```

当前消息的上下文通常已经包含：

- Conversation ID
- Service URL
- Channel ID
- Tenant ID
- 用户信息
- Bot 信息
- Reply-to Activity ID

因此，后端可以通过 Teams SDK 当前消息处理器中的 `send()` 或对应回复方法，将消息发送回原来的会话。

示意代码：

```typescript
app.on("message", async ({ activity, send }) => {
  const question = activity.text?.trim();

  if (!question) {
    await send("请输入需要查询的问题。");
    return;
  }

  await send({ type: "typing" });

  const answer = await agent.process({
    question,
    teamsUserId: activity.from.id,
    conversationId: activity.conversation.id,
  });

  await send(answer);
});
```

实际事件对象和 API 名称应以项目使用的 Teams SDK 版本及模板为准。

### 3.2 回复消息的网络方向

回复当前消息时，后端不是直接连接用户电脑，也不需要知道用户 IP。

网络方向如下：

```text
Chatbot Backend
    ↓ Bot Connector / Teams Channel
Microsoft Teams
    ↓
当前用户的 Teams 客户端
```

Teams 平台根据当前 Conversation Context，将回复投递到正确的一对一聊天、群聊或频道会话。

### 3.3 主动推送消息

主动推送是指没有正在处理的用户消息时，由 Chatbot 后端主动发起 Teams 消息。

例如：

```text
监控系统发现服务器宕机
→ 触发 Chatbot 后端
→ Chatbot 主动向值班人员发送 Teams 告警
```

又例如：

```text
工单状态发生变化
→ Chatbot 主动通知工单申请人
```

主动消息的流程为：

```text
后台事件或定时任务
→ Chatbot 后端读取保存的 Conversation Reference
→ 通过 Bot Connector 创建或继续会话
→ Teams 将消息投递给目标用户或会话
```

### 3.4 主动推送需要保存的信息

为了以后向同一个用户或会话主动发送消息，后端通常需要在用户首次与 Agent 交互或安装 Agent 时保存 Conversation Reference，包括：

```text
Conversation ID
Service URL
Channel ID
Tenant ID
Bot ID
User ID
```

这些信息应保存到受控的数据存储中，例如：

- Azure Cosmos DB
- Azure SQL Database
- SQL Server
- PostgreSQL
- Azure Table Storage

不要只保存在进程内存中，否则服务重启或横向扩容后会丢失。

### 3.5 主动推送的限制和注意事项

主动消息通常需要满足：

- 用户已经安装或使用过该 Teams Agent
- 后端保存了有效的 Conversation Reference
- Bot 身份配置正确
- 后端可以访问 Bot Connector 服务
- 目标用户仍然有权使用该应用
- Service URL 和租户信息与目标会话匹配

还应增加以下治理措施：

- 限制通知频率
- 防止重复告警
- 提供退订或静默策略
- 区分信息、警告和严重告警
- 记录主动消息发送审计日志
- 避免在通知中暴露敏感数据

### 3.6 推荐实施顺序

第一阶段只实现当前消息回复：

```text
用户问
→ Chatbot 收到消息
→ Agent 处理
→ Chatbot 回复原会话
```

第二阶段再实现主动推送：

```text
监控或业务事件
→ Chatbot 主动发送通知
```

这样可以先验证最核心的端到端消息链路，降低第一版的开发和排障复杂度。

## 4. 最小验证清单

在继续接入 Azure OpenAI 和内部 Tool 之前，建议先完成 Echo 测试。

用户在 Teams 中发送：

```text
hello
```

后端返回：

```text
你发送了：hello
```

Echo 成功说明以下链路已经打通：

```text
Teams
→ Teams/Bot Channel
→ Azure Bot Resource
→ 公网 Messaging Endpoint
→ WAF/反向代理
→ 自建 Chatbot 后端
→ Bot Channel
→ Teams 用户
```

完成 Echo 测试后，再逐步替换为：

```text
Teams Message
→ Agent Orchestrator
→ Azure OpenAI Tool Calling
→ Internal API / DB
→ 最终回答
→ Teams
```
